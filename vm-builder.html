Mission Briefing: Provision Your First Virtual Machine

The Foundry District is expanding into the cloud, and you've been asked to set up its first virtual machine (VM).

A virtual machine is a complete computer — operating system, storage, memory — that runs as software on top of a physical computer. The physical computer is called the host, and the machine you're about to build is a guest. A special software layer called a hypervisor divides the host's real hardware among its guests.

What you'll do in this lab

You'll follow the same steps a cloud engineer follows when creating a real VM: choose a name and region, pick an operating system, select a size (and see what it costs per hour), create an administrator account, review, and create. Then you'll manage your running VM — starting, stopping, snapshotting, and deleting it — while a billing meter runs, just like in a real cloud. Starting in Week 6, the Lab Portal will hand you a real Azure VM built through this exact process — you'll recognize every step, because you did it here first.

Heads up — things can go wrong on purpose. Real cloud platforms reject taken names, refuse weak passwords, and sometimes fail to provision. This simulator does too. Reading an error message calmly and fixing the problem is a core professional skill — errors here are part of the lab, not a mistake you made.

Step 1 — Basics: Name & Region

Every VM needs a unique name and a home datacenter. Cloud platforms enforce naming rules — this one uses the same rules as Azure.

○ Between 3 and 24 characters
○ Only lowercase letters, numbers, and hyphens
○ Starts with a letter
NameNotAvailable: a VM named already exists in this account. Names must be unique — pick another. (Yes, even the example name gets taken in real life.)
Why naming matters: In a real company, one cloud account can hold hundreds of VMs. Names like web-server-prod-01 tell you at a glance what a machine does. Vague names like test123 cause real security incidents — nobody knows what's safe to shut down.
RECOMMENDED
Foundry Central
Closest to you. Lowest latency — your commands reach the VM fastest.
HIGH DEMAND
Foundry East
The most popular region. Often runs near capacity — provisioning can fail when it's full.
STANDARD
Foundry West
Farther away — slightly higher latency. Often used for backups and redundancy.

Step 3 — Choose a VM Size

Cloud platforms sell VMs in named sizes — fixed bundles of CPU, memory, and disk, each with an hourly price. The meter runs for every hour the VM exists in a running state. Choose a size, and watch the host's resources get carved up below.

License fee applies: you picked Windows Server, which adds $0.046/hr on top of the size price. Linux VMs skip this fee — one reason most cloud servers run Linux.

Host machine resources (the physical computer)

CPU0 of 8 cores allocated to your VM
RAM0 of 32 GB allocated to your VM
Disk0 of 512 GB allocated to your VM
Notice: the host never gives everything away. It keeps resources for itself and for other VMs it might run. In real datacenters, one powerful host runs dozens of guest VMs at once — that sharing is what makes cloud computing affordable.

Step 4 — Create the Administrator Account

Every new VM needs an administrator account — the account you'll use to sign in and manage it. This is the most security-critical choice in the whole process: this account has full control of the machine.

○ Between 3 and 20 characters (letters, numbers, hyphens)
○ Not a name attackers guess first (admin, administrator, root, user, guest, test)
Why the blocklist? Automated attacks hammer every server on the internet trying usernames like admin and root thousands of times a day. Real cloud platforms refuse them for exactly this reason.
Strength: —
○ At least 12 characters
○ Uppercase and lowercase letters
○ At least one number
○ At least one symbol (!@#$%…)
Professional habit: never reuse a password you use anywhere else, and store server credentials in a password manager — not a sticky note, not a text file on your desktop. In Week 8 you'll learn key-based authentication, which is stronger than any password.

Lifecycle checklist

  • ⬜ Stop your VM — then watch what happens to the billing rate
  • ⬜ Start it again
  • ⬜ Take a snapshot (a saved copy of the VM's exact state you can roll back to)
  • ⬜ Delete the VM — the only way to stop paying entirely

Delete this virtual machine?

Deleting a VM permanently destroys its virtual disk and everything on it. In a real cloud platform there is no undo — this is why administrators take snapshots first. Your snapshot means you could rebuild. Deleting is also the only way to stop all billing. Proceed?
